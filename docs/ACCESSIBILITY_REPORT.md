# Accessibility report — Utsav

Honest, evidence-first record of the accessibility work done in Phase 3. Engineering
target: **WCAG 2.2 Level AA, where applicable**. This is not a certification or a formal
conformance claim; it is a scoped audit with reproducible evidence.

## Executive summary

- **Target:** WCAG 2.2 Level AA, where applicable. This is an engineering target and a scoped
  audit. It is not a certification or a conformance claim.
- **Automated result:** automated scans found zero serious or critical axe violations in the
  recorded tested states: 10 views (8 populated views plus the setup and events-library
  first-run states) in light and dark themes, 20 view/theme states in all, each with a
  machine-readable result file.
- **Manual and scripted checks:** a keyboard-only journey, a 320 px reflow check, a tablet
  walk and a reduced-motion check are scripted in `e2e/specs/` and pass.
- **Defects found and fixed:** six real defects found by the first audit run were fixed
  (listed in section 3).
- **Not done:** no real screen-reader testing (NVDA or VoiceOver) was performed. Automated
  results do not prove complete WCAG conformance.

Evidence files (generated by `e2e/specs/accessibility.spec.ts`, one per view and theme):
[`e2e/evidence/accessibility/`](../e2e/evidence/accessibility/), for example
[budget-light.json](../e2e/evidence/accessibility/budget-light.json) and
[budget-dark.json](../e2e/evidence/accessibility/budget-dark.json). Each file records the
axe tags used (`wcag2a`, `wcag2aa`, `wcag21a`, `wcag21aa`, `wcag22aa`), a timestamp and the
violations list. The recorded `violations` list is empty in all 20 files.

## 4. Manual verification

Method: keyboard-only walks of the real production build (Chromium, headless, the same
build CI tests), recorded in `e2e/specs/accessibility.spec.ts` ("Keyboard-only
operation"):

- Skip link is the first stop and moves focus to `#main` on Enter.
- The full setup form can be completed and submitted with the keyboard alone.
- Arrow keys move and activate tabs; Home/End jump to the ends.
- No keyboard trap: a 20-press Tab walk lands on more than 6 distinct stops.
- Focus is visible: `:focus-visible` outline (`outline-style: none` would fail the test).
- Destructive "Reset" flow is fully keyboard operable and confirmed before it acts.

Contrast: token-level math is asserted in `tests/ui/tokens.test.ts` (both themes);
axe re-verifies rendered output per view/theme. Reflow: 320 px scan in the same spec,
plus a 768 px tablet walk (`e2e/specs/responsive.spec.ts`). Reduced motion:
`prefers-reduced-motion: reduce` collapses transitions to 0.01 ms (asserted).

Colour is never the only signal: payment states (PAID/OVERDUE/partly paid — words),
RSVP badges (Coming/Not coming/Waiting for reply), warnings (icon + word), over-budget
(⛔ + amount), AI fallbacks (explicit "offline" text).

## 5. Screen-reader results

**Not performed.** No screen reader is available in this build environment, and the
project rules forbid claiming verification that did not happen. What exists instead:
semantic structure verified by axe (roles, names, labels, heading order, landmarks) and
`aria-live`/`role="status"`/`role="alert"` regions for autosave, action notices, dropped
events and patch previews. Screen-reader testing with NVDA/VoiceOver remains open work.

## 6. Remaining limitations

1. Screen-reader interaction untested (above).
2. The axe runs cover rendered states of the walkable journeys; states only reachable
   by unusual data (e.g., storage-recovery card under a screen reader) were checked by
   code review of their semantics, not by a live scan.
3. Zoom beyond the 320 px-reflow test (e.g., 400% at 1280) is not separately scripted;
   the reflow invariant tested (no page-level horizontal scroll, tables scroll inside
   their own box) is the same mechanism.
4. `list`-style charts do not exist in the product; the readiness `progress` element
   carries an `aria-label` with the percentage.
